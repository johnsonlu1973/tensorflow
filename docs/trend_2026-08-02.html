# SoC 策略分析報告 **分析週期**：2026 年第 30 週（7/26-7/28） --- ## 任務一：結構性機會偵測 --- ### 機會 1：離線 / 端側 LLM 推論在受監管與敏感資料場景的專用 SoC 空間 #### Step 1：事實觀察 - [Android Authority, 2026-07] "Google Gemma 4 在您的口袋中：如何完全離線執行最新 AI" → 事實：Google 已釋出可完全離線運行於手機的 Gemma 4 模型 - [科技新報, 2026-07] "Meta 員工自建 AI 用量排行榜秀 30 天就破 60 兆 Token，但資料外流迅速撤下" → 事實：即使企業內部工具，員工 AI 使用行為（Prompt 內容）本身也構成敏感資料，Meta 已因外流風險撤下 - [SemiEngineering, 2026-07] "邊緣 AI 無所不在、代理型、多模態且硬體加速" → 事實：邊緣 AI 產業論述已從「推論加速」轉向「代理型多模態」 - [TechCrunch AI, 2026-07-27] "提醒：你的 Claude 共享聊天和 Artifacts 可能已被 Google 索引" → 事實：雲端 AI 服務的分享機制已多次導致意外資料外流 - [iThome, 2026-07-27] "非人類身分治理成企業新課題，CSA發布NHI治理報告" → 事實：AI Agent 產生的非人類身分（NHI）已成企業合規新項目 #### Step 2：條件變化分析 **改變的條件**：可在 8GB 記憶體、行動級 NPU 上執行的模型能力，從「玩具等級」跨越到「可完成企業級文件草擬、程式碼理解」的實用門檻。 - **時間點**：2025 年底至 2026 年初（Gemma 3 → Gemma 4、Llama 3.2 → 更小的高能力模型陸續釋出） - **改變性質**：技術性（模型壓縮 / MoE / Distillation）＋ 監管性（GDPR、企業內部資料外流事件累積）雙重驅動 - **兩年前不存在的原因**：2024 年可離線執行的模型能力太弱，無法完成「編輯 Word 文件」「總結企業郵件」等 JTBD - [推斷] 標記（技術可行性有來源；監管壓力來自事件累積推斷） #### Step 3：趨勢導出 - **Q1（什麼變了）**：端側模型能力跨越「實用門檻」 - **Q2（機制）**：能力跨越門檻 → 企業 CIO 首次有選擇權，可將敏感 workload 保留在裝置端而不犧牲功能 → 採購決策的評估維度從「雲端 AI 服務比較」擴展到「端 vs 雲的部署選擇」 - **Q3（為何此時足夠）**：三個門檻同時跨越——(a) 模型能力足夠處理白領日常任務、(b) NPU 效能足夠支撐即時互動延遲、(c) 資料外流事件（Suno 5,530 萬帳號、Meta 60 兆 Token 排行、Claude 索引事件）在同一週集中爆發，使 CIO 的「雲端 AI = 資料風險」認知從個別事件變成系統性擔憂 - **Q4（反事實）**：若模型能力未跨越門檻（仍是 2024 年的 3B 玩具），CIO 即使有資料擔憂也只能接受雲端方案——趨勢會被壓抑 **趨勢**：企業 AI 部署從「雲端優先」轉向「敏感 workload 端側化、通用 workload 雲端化」的混合架構。 驗證： - ✅ 宏觀性：影響整個企業 IT 採購邏輯 - ✅ 長期性：模型效率曲線持續改善為結構性驅動力 - ✅ 不可逆性：資料外流事件不會回頭 #### Step 4：市場新機會浮現 - **Q1（競爭條件變化）**：原本「端側 AI SoC」的競爭條件是 TOPS 數字競賽（Qualcomm 45 TOPS、Apple M 系列 XX TOPS），現在變成「在給定 TDP 下能持續運行 8-14B 模型並維持 >15 tokens/sec 的實務效能」 - **Q2（機制）**：企業採購方開始問「這台筆電 / 手機能不能離線跑我們公司的內部 Copilot」→ OEM 被迫向上游 SoC 廠要求「可跑 XX 模型」的 spec sheet → SoC 差異化從 TOPS 轉向「模型-記憶體頻寬-功耗」三角優化 - **為何現有競爭者未滿足**： - Qualcomm/MediaTek 的 NPU 架構在 2023-2024 定案時，優化目標是 CNN 影像 / 語音，不是 Transformer 的 KV Cache 頻寬瓶頸 - Apple 有能力但選擇不做 B2B 授權（商業模式衝突） - NVIDIA 在此規模下 TDP 不符合行動 / 筆電 - **Q4（反事實）**：若趨勢不存在（雲端 AI 無資料風險），企業會直接用雲端，端側 SoC 只需跑 3B 助理，市場空間小 10 倍 **市場新機會**：專為「7-14B Transformer 推論」優化記憶體子系統與 KV Cache 管理的行動 / 筆電 SoC，賣給需要離線企業 AI 的 OEM。 #### Step 5：目標客群與 JTBD **問題 A：為什麼是 X，不是其他？** 看似相關但排除的客群： - **消費級手機 OEM**（Samsung / Xiaomi）：排除，因消費者對「離線 AI」支付意願低，會選擇免費雲端服務——他們的痛點是「便宜」不是「隱私」 - **一般企業筆電 OEM**（Dell / HP 大宗機種）：排除，因採購決策由 IT 部門主導但預算敏感，不會為端側 AI 付溢價 - **超高階遊戲筆電**：排除，工作負載不是 AI 推論 **目標客群**：**受嚴格資料監管的行業專用終端 OEM**——具體包括醫療 / 律師事務所 / 金融合規 / 政府特殊部門用的商用筆電與平板 OEM（如 Panasonic Toughbook、Getac、Dynabook、Lenovo ThinkPad 特定 SKU） **問題 B：結構性支付意願** 這些客群的處境：他們的客戶（醫院、律所、政府）**無法接受**任何雲端 AI 方案（HIPAA、律師-客戶特權、機密資料），但**必須**採用 AI 以維持競爭力。這使 OEM 的 BOM 溢價空間從消費機的 5% 提升到 30-40%。 **問題 C：有能力的廠商為何未解決？** - **選擇不做（利益衝突）**：Qualcomm 的主要營收來自消費手機，為此小眾市場重新設計記憶體子系統會拖慢主流 SoC roadmap - Apple 的商業模式是垂直整合，不對外授權 **JTBD**：「當我（Toughbook 產品經理）為 2027 醫療機種選擇 SoC 時，我需要一顆能在 15W TDP 下持續運行 8-13B 模型、tokens/sec > 20 的晶片，讓我能向醫院採購方證明『這台筆電上的 AI 完全不連網』。」 #### Step 6：痛點 - **具體阻礙環節**：現有行動 SoC 執行 8B 模型時，**記憶體頻寬**（而非算力）成為瓶頸——LPDDR5X 頻寬 ~68GB/s，8B 模型每 token 需讀取 ~8GB 權重，理論極限 ~8.5 tokens/sec，實測更低 - **現有方案為何無法改善的機制**： - 增加 LPDDR 頻寬 → 功耗上升（違反 15W TDP） - 換 HBM → 成本與封裝面積不適合行動平台 - 現有 NPU 沒有針對 Transformer KV Cache 的 on-chip SRAM 層級架構 - **Q4（反事實）**：若記憶體頻寬非瓶頸，OEM 會直接用現成 Qualcomm/MediaTek——痛點消失 - **痛點深度**：以行業筆電 ASP $2,500-4,000、AI 差異化溢價 $500-1,000 估算，OEM 願為此付 $30-80 SoC 溢價 **核心痛點**：15W 級 SoC 無法以商用速率運行 8B+ Transformer，成為端側企業 AI 的產品化障礙。 #### Step 7：客戶價值 **解決方案**：SoC 內建大容量 on-chip SRAM（32-64MB）＋ Transformer-native NPU 架構＋ KV Cache 專用管理單元。 - **機制**：將 KV Cache 與熱權重駐留 on-chip SRAM，減少 60-70% LPDDR 存取 → 相同 TDP 下 tokens/sec 提升 2-3 倍 - **效益**：OEM 可推出「離線企業 AI」差異化機種，ASP 溢價 $500-1,000 - **成本**：晶片 BOM 溢價 $30-80、驅動 / 模型移植工程 6-9 個月 - **效益 > 成本**：$500 ASP 溢價 vs $80 BOM，毛利改善明顯 - **競爭壁壘**：Qualcomm 下一代 SoC tape-out 週期 18-24 個月，若在 2026 定案，2028 才上市——時間窗口約 24-30 個月 - **Q4（反事實）**：痛點不存在則無客戶價值——確認因果 #### Step 8：商業價值 **商業模式**：專用 SoC 授權或 IP + 參考設計，賣給行業筆電 / 平板 OEM。 - **擷取機制**：SoC ASP $80-150（vs 消費 SoC $40-70），毛利率 55-65% - **定價權來源**： - 架構壁壘：Transformer-native NPU 與記憶體子系統的協同設計 - 轉換成本：OEM 一旦選定，模型優化 / 工具鏈投入 6-9 個月工程時間 - **護城河動態**： - 加深機制：與模型社群（Gemma / Llama 家族）建立針對此 SoC 的 quantization recipe，形成軟體生態 - 削弱威脅：Qualcomm 2028 世代 SoC 若跟進，架構優勢消失 - 護城河頂峰：2027 上半年 - **商業價值上限**：假設 3 年窗口、目標市場（行業筆電 + 專用平板）年 500-800 萬台、滲透率 15-25%，年營收 $100-300M [推斷，市場規模需驗證] - **市場規模**：[未驗證，建議搜尋 rugged / vertical laptop 全球 TAM] --- ### 機會 2：AI Agent 的執行環境安全與可觀測性 SoC / SoM 層級整合 #### Step 1：事實觀察 - [The New Stack, 2026-07] "Diagrid 為失敗的 AI agents 提供恢復機制" → 事實：AI Agent 生產環境的可靠性成為新市場 - [iThome, 2026-07-27] "中國駭客組織JadeProx 利用 AI 代理 Hermes 攻擊泰國財政部" → 事實：AI Agent 已被用於實際網路攻擊 - [iThome, 2026-07-27] "非人類身分治理成企業新課題，CSA發布NHI治理報告" → 事實：AI Agent 身分治理已成合規新項目 - [The New Stack, 2026-07-27] "MCP 最大更新移除許多伺服器依賴的機制" → 事實：Agent 通訊協定 MCP 正在標準化 - [SemiEngineering, 2026-07] "邊緣 AI 無所不在、代理型..." → 事實：邊緣端 Agent 已成產業論述主軸 #### Step 2：條件變化分析 **改變的條件**：AI Agent 從「示範概念」變成「有實際攻擊 / 損害紀錄」的執行實體。 - **時間點**：2026 上半年（Hermes 攻擊、Fast16 自主分析等實例集中出現） - **改變性質**：安全性 + 監管性 - [推斷] #### Step 3：趨勢導出 - **Q1**：Agent 從「工具」變成「有身分、有攻擊面、有損害紀錄的執行實體」 - **Q2**：企業安全長被迫將 Agent 納入資安治理 → 需要在 Agent 執行環境（不只軟體層）建立可稽核的信任錨 - **Q3（為何此時）**：MCP 協定標準化 + 實際攻擊事件 + NHI 治理框架同時出現，形成「必須治理」的臨界壓力 - **Q4**：若無實際攻擊案例（僅有假想風險），企業不會為此增加硬體成本——趨勢會被壓抑到軟體層 **趨勢**：企業級 AI Agent 部署將從純軟體治理走向「硬體信任根 + 軟體治理」的雙層架構。 驗證：✅ 宏觀、✅ 長期、✅ 不可逆 #### Step 4：市場新機會浮現 - **Q1（競爭條件變化）**：伺服器 / 邊緣 SoC 的差異化從「AI 算力」擴展到「Agent 執行的硬體隔離、身分證明、行為稽核」 - **Q2（機制）**：企業採購 Agent 平台時開始要求「可證明的執行環境」→ 平台廠向下要求硬體支援 → SoC 廠需提供 Agent-specific TEE / Attestation 能力 - **為何現有廠商未滿足**： - Intel SGX / AMD SEV / ARM CCA 是為「一般機密運算」設計，不是為 Agent 生命週期優化 - 現有 TEE 對頻繁 attestation（每個 tool call）的效能開銷不可接受 - **Q4**：若無實際安全事件，企業會停留在軟體層——確認機會依賴趨勢存在 **市場新機會**：為 AI Agent 生命週期優化的**輕量化持續 attestation** 硬體引擎，整合到伺服器 / 邊緣 SoC。 #### Step 5：目標客群與 JTBD **問題 A**： - 排除：一般雲端 CSP——他們有自建能力（Google Titan、AWS Nitro），不會採購第三方 - 排除：純消費 SoC——Agent 主要跑在企業 / 邊緣 - **目標客群**：**企業私有雲 / 主權 AI 資料中心的伺服器 OEM**（Supermicro、Wiwynn、Quanta、Foxconn 資料中心產品線），以及**邊緣 AI 閘道 OEM** **問題 B**：這些 OEM 的客戶是不能上公有雲的政府 / 金融 / 電信——他們無法自建 attestation IP，需要 SoC 內建方案 **問題 C**： - Intel/AMD 選擇不做：他們的 TEE 商業模式綁定既有 x86 生態，難以為 Agent 場景重構 - ARM 的 CCA 尚在標準化，時程未定 **JTBD**：「當我為主權 AI 資料中心設計伺服器板時，我需要一個 SoC 或 SoM 能為每個 Agent 實例提供 <1ms 開銷的 attestation，讓客戶（政府）能稽核每個 tool call。」 #### Step 6：痛點 - **阻礙**：現有 TEE 的 attestation 開銷（10-100ms）在 Agent 高頻工具呼叫下不可接受 - **無法改善的機制**：現有 TEE 為「長生命週期 enclave」設計，Agent 是「短生命週期、高頻切換」的相反工作負載 - **Q4**：若無 Agent 場景，這個痛點不存在——確認 - **痛點深度**：主權 AI 專案採購金額動輒 $10M+，SoC 佔 BOM 5-10%，願意付溢價 **核心痛點**：現有硬體信任根架構與 Agent 高頻執行模式不匹配。 #### Step 7：客戶價值 **解決方案**：整合 Agent-specific attestation engine（可能是 RISC-V 協處理器）到伺服器 / 邊緣 SoM - **機制**：專用硬體加速的短生命週期 attestation，開銷降至 <1ms - **效益**：OEM 可打入主權 AI / 監管密集市場 - **成本**：SoC / SoM BOM 溢價 $50-200 - **競爭壁壘**：Intel/AMD 因架構包袱難以快速跟進，窗口 24-36 個月 #### Step 8：商業價值 - **擷取機制**：SoM / SoC IP 授權 + 參考設計 - **定價權**：架構壁壘（RISC-V based 專用架構） - 注意：[科技新報] 三星 SSD 控制器導入 RISC-V 顯示 RISC-V 進入商用系統晶片的成熟度已足夠 - **護城河動態**：與 Agent 平台廠（Anthropic Managed Agents、Diagrid、Dynatrace）建立 attestation 標準——加深護城河 - **市場規模**：[未驗證] 主權 AI + 監管邊緣 AI 伺服器 TAM，建議搜尋確認 --- ### ✅ 任務一因果鏈完整性審核

--- ## 修正說明 ### 修正 1（對應 M1-3） **修正**：「混合架構趨勢 → SoC 差異化從 TOPS 轉向記憶體頻寬」 **原因**：記憶體頻寬瓶頸是「跑大模型」的通用瓶頸，不專屬於企業混合架構。即使沒有企業趨勢，消費端跑更大模型（Gemma 4 手機版）也會推動同方向轉變。因此「混合架構」不是這個轉變的必要原因。 **正確因果**：**「模型規模跨越 7B+ 門檻」→ SoC 差異化從 TOPS 轉向記憶體頻寬**。企業混合架構趨勢是**放大器**（提高溢價空間），不是**起因**。 **不受影響**：機會 1 的市場空間存在性不受影響——企業混合架構仍是「支付意願」的來源（M1-5 通過反事實測試），只是「技術瓶頸的成因」需修正為更根本的模型規模驅動。 --- ### 修正 2（對應 M1-6） **修正**：「Qualcomm 消費營收佔比 → 不會為行業筆電重構架構」 **原因**：Qualcomm 已有 Snapdragon X（PC）與 Automotive 分支，證明他們願意為非消費場景做架構投入。真正的機制不是「營收佔比」，而是「最小可行市場門檻」。 **正確因果**：**「行業筆電 TAM 低於 Qualcomm 新架構分支的最小可行門檻（推估 >500 萬台/年）」→ Qualcomm 不會為此單獨投入新架構**。這是機會存在的真正結構性原因。 **不受影響**：機會 1 的目標客群定義（行業筆電 OEM）與 JTBD 不受影響；但**商業價值上限的估算需要重新驗證**——如果行業筆電 TAM 接近 Qualcomm 門檻，機會窗口會被壓縮。建議搜尋 rugged / vertical laptop 全球年出貨量以驗證。 --- ### 修正 3（對應 M1-7） **修正**：「模型社群為此 SoC 優化 → 護城河隨時間加深」 **原因**：存在雞生蛋問題——社群優化需要裝機量，裝機量需要生態支持。護城河不會「自動」加深。 **正確因果**：**「達到 X 萬台裝機量門檻」→ 社群優化投入 → 護城河加深**。需要主動策略（例如：初期補貼開發者、提供優化服務）跨越門檻。 **不受影響**：機會 1 的短期客戶價值（M1-4、M1-5）與 24-30 個月時間窗口估計不受影響；但**長期護城河的成立需要額外的生態策略**，不能假設自動發生。 --- ### 修正 4（對應 M2-3） **修正**：「硬體治理趨勢 → 必須有 SoC 專用 attestation 引擎」 **原因**：軟體層改善（更輕量的 TEE runtime、Confidential VM 優化）是可能的替代路徑，未證明必須走硬體。 **正確因果**：**「Agent 高頻工具呼叫（>100 次/秒）＋ 軟體 TEE 開銷下限（受記憶體加密硬體限制）→ 純軟體方案無法達到 <1ms 目標」→ 硬體引擎成為必要**。但這個因果依賴一個**未驗證的前提**：實務 Agent 部署真的需要 <1ms attestation。 **修正後標記**：機會 2 應標為 **[未驗證 - 需驗證 Agent 部署的 attestation 頻率與延遲需求]**。若實務只需 10-50ms，軟體方案足夠，機會 2 不成立。 **不受影響**：機會 1 的分析完全不受影響（不同技術領域）。機會 2 的**趨勢層**（硬體治理成為新方向）分析仍成立，只是**專用 SoC 引擎作為解方**的必要性需驗證。 --- ### 修正 5（對應 M2-5） **修正**：「Intel/AMD 商業模式綁定 → 難以為 Agent 場景重構」 **原因**：未說明「商業模式綁定」如何具體阻礙。Intel TDX、AMD SEV-SNP 都在持續演進，此推論過強。 **正確因果 [推斷]**：**「Intel/AMD 現有 TEE roadmap 已定案至 2027，加入 Agent-specific 特性需等下一世代」→ 存在 24-30 個月時間窗口**。這是**時間問題**（挑戰選項 D），不是**能力問題**。 **不受影響**：機會 2 的時間窗口估計（24-36 個月）方向正確，但**護城河的持久性下修**——一旦 Intel/AMD 下世代加入類似特性，架構優勢會被追平。長期護城河需依賴生態綁定而非技術獨占。 --- ### 修正 6（對應 M2-6） **修正**：「三星 SSD 用 RISC-V → RISC-V based Agent attestation 引擎商用成熟」 **原因**：跨域類比。SSD 控制器是效能場景，attestation 是安全場景，驗證流程與威脅模型完全不同。 **正確因果**：三星案例僅證明 **RISC-V 生態、工具鏈、供應鏈的商業成熟度**足夠支撐商用晶片開發，**不證明**其安全屬性適合 attestation。 **不受影響**：機會 2 的市場需求分析與痛點分析不受影響；但**技術路徑選擇（RISC-V vs ARM CCA vs 客製 ISA）需要獨立評估**，不能以三星案例作為選擇 RISC-V 的依據。 --- ## 審核總結 -
